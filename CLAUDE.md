# CLAUDE.md

## Mandatory Rules

1. Before pushing: `make lint` then `make test`. Both require `mise install` once per clone — every tool and the Go toolchain are pinned in `mise.toml`, and the Make targets invoke them through `mise exec`. CI runs these same two targets, so a local verdict and a CI verdict cannot disagree.
2. Prefer **Serena MCP** for symbol-level code operations:
   - `get_symbols_overview` / `find_symbol` over full file reads when navigating
   - `replace_symbol_body` / `insert_after_symbol` / `insert_before_symbol` for symbol edits
   - `find_referencing_symbols` for impact analysis before changes
   - Edit/Write are fine for new files, non-code files, and non-symbol edits (imports, comments, formatting)
3. Use **sequential thinking MCP** for complex reasoning
4. Use **ref MCP** for library documentation lookups
5. After code changes, update `.skills/` files if CLI commands, flags, behavior, or workflows changed
6. ALWAYS follow the instructions in the global $HOME/.claude/CLAUDE.md

## Project Overview

Go CLI for template-driven code generation and project scaffolding. Uses Gonja (Jinja2-compatible) templates with `{{ vars.* }}` namespace.

For command reference and template authoring details, see `.skills/SKILL.md` and `.skills/reference.md`.

## Commands

```bash
# Build
make build                              # Build binary to ./tag
make install                            # Build and install to ~/.local/bin

# Test
make test                               # All tests with coverage (what CI runs)
make test-integration                   # Integration tests only
go test ./...                           # All tests, ambient toolchain
go test -v ./internal/scaffold/...      # Specific package
go test -run TestUT_CommandError ./...   # Single test

# Lint & Format
make lint                               # go vet + deadcode + golangci-lint (what CI runs)
make fmt                                # Format (gofumpt + goimports)
make scan-code                          # gosec (what the CI scan job runs)
make scan-deps                          # govulncheck (weekly schedule, never gates a PR)
make scan                               # Both
make tools                              # Install the pinned toolchain (mise install)
```

## Conventions

### Error Handling
```go
if err != nil {
    return app.Errorf("cannot open file: %w", err)
}
```
Errors bubble up via `*CommandError` to `main.go` for centralized logging and exit codes.

### Testing
- **Assertions**: testify (`assert`/`require`)
- **Style**: Table-driven tests preferred
- **Naming**: `TestUT_*` (unit), `TestIT_*` (integration)
- **Unit tests**: Mock interfaces (e.g., `MockPrompter`), no real filesystem/TTY
- **Integration tests**: `t.TempDir()` for isolation, live in `internal/integration/`
- **Gotcha**: Tests using `setupFakeLibrary` must NOT use `t.Parallel()` (mutates package-level var)
- **HTTP tests**: `httptest.NewServer` with parameterized base URLs

### Linting
- Config: `.golangci.yaml` — `default: all` with ~30 disabled linters
- Key limits: `cyclop` max 20, `funlen` max 100 lines / 60 statements, `gocognit` max 30
- Imports: `goimports` with local prefix `github.com/kaikenlabs/tag`
- Test files get relaxed rules (no `dupl`, `gosec`, `funlen`, `cyclop`, etc.)

### CI
PR checks (`.github/workflows/ci.yml`): three jobs, `lint`, `scan` and `test`, which run `make lint`, `make scan-code` and `make test` — the same targets used locally. `make scan-deps` (govulncheck) is deliberately NOT a PR check: its findings appear when an advisory is published, not when code changes, so it runs weekly from `.github/workflows/vulncheck.yml` instead. Tool and Go versions come from `mise.toml`, installed by `jdx/mise-action`; `go.mod`'s `go` directive must agree with the Go pin there or `GOTOOLCHAIN=local` fails the build.

## Lessons Learned

- **`mise.toml` is the ONLY place a tool or Go version may appear — CI runs `make lint`/`make test`, not its own copy of them**: before #369, `ci.yml` re-implemented the gate and pinned golangci-lint separately from `mise.toml`, while `scripts/tools.mk` installed everything `@latest` into `bin/`. The three drifted until `make lint` reported 74 issues on a clean `main` and CI reported 0. `scripts/tools.mk` and `bin/`/`GOBIN` are gone; `make tools` is `mise install`. If you add a tool, pin it in `mise.toml` and call it through `$(MISE)` (`mise exec --`) — never bare `PATH`, which is exactly how the stale 2.12.2 binary shadowed the 2.10.1 pin. `grep -rn '2\.1[0-9]' .github/ scripts/ Makefile mise.toml .tool-versions` must return one hit.
- **Bumping the Go pin does NOT rebuild the `go:` tools — force them, or you get "green in CI, broken locally"**: mise keys a `go:` backend install on the *tool's* version, not the Go that compiled it, so after moving `mise.toml` from 1.25.13 to 1.26.6 `mise install` said "all tools are installed" while `govulncheck` died with `package requires newer Go version go1.26 (application built with go1.25)`. govulncheck 1.7.0 was already the latest release — there was nothing to bump to. CI never sees this: `jdx/mise-action` compiles every `go:` tool fresh on a clean runner. The last step of any Go bump is therefore `GOTOOLCHAIN=auto mise install --force "go:<path>@<version>"` for all five (`deadcode`, `goimports`, `gofumpt`, `gosec`, `govulncheck`). Note plain `mise uninstall "go:<path>"` without the `@version` errors out.
- **`golangci-lint`, not the compiler, is the ceiling on how far the Go pin can move**: `golangci-lint version` reports what Go built it, and it hard-refuses a module targeting anything newer. 2.10.1 is built with go1.26.0, which is exactly why 1.26.6 was taken and go1.27.0 (stable as of 2026-08) was not — 1.27 would need a golangci-lint release built with go1.27, and bumping that pin is the #369 landmine. Check `golangci-lint version` BEFORE deciding a target Go version.
- **`go.mod`'s `go` directive and the `mise.toml` Go pin must match, and `GOTOOLCHAIN=local` in the Makefile enforces it**: they disagreed (1.25.7 vs 1.25.6) and that — not the `gotest` wrapper the ticket blamed — is why `make test` did not compile. mise exports `GOROOT` for its pinned Go while `GOTOOLCHAIN=auto` re-execs the driver into whatever `go.mod` demands, and the mismatch surfaces as `compile: version ... does not match go tool version ...` on every stdlib package. `GOTOOLCHAIN=local` converts a future mismatch into a one-line explanation. The `tools` target overrides it back to `auto` on purpose: third-party tools legitimately need their own toolchain (gosec 2.28.0 requires go >= 1.25.8), which is unrelated to this module's.
- **`make test` must keep `-count=1`, and `internal/integration/main_test.go` must keep building the binary**: those two together are the only thing making the subprocess tests real. They used to `t.Skip` when `./tag` was absent, so CI — which never ran `go build` — skipped them silently for their entire life, and a stale `./tag` at the repo root would be tested instead of HEAD. `TestMain` now builds into a temp dir. Drop `-count=1` and it regresses invisibly: `internal/integration` does not import package `main`, so editing `main.go` leaves the cache key untouched, the package reports `(cached)`, and `TestMain` never runs. Verified both directions before merge.
- **`deadcode` exits 0 on findings, so `scripts/lints.mk` checks its OUTPUT, not just its status**: the recipe fails on a non-zero exit *or* any stdout. Do not "simplify" it back to a bare `deadcode -test ./...` — that line was decorative from the day it was added, and `deadcode ./...` still reports 15 unreachable funcs on this repo (the `-test` flag counts test-only callers as roots, which is why the gate is clean).
- **`make scan-code` is a gate now, and the five excluded gosec rules in `scripts/lints.mk` are a deliberate list — extend it only with a reason recorded here** (#372): `G304`/`G703` (path from a variable, on read and on write) are 78 of the original 120 findings and are structural in a code generator whose entire job is reading and writing caller-supplied paths; annotating them 78 times says nothing a reader could act on. `G104` (27) is unhandled errors, all of them deliberate cleanup-path ignores (`out.Close()` on an error return, `os.RemoveAll` on rollback, `tw.Flush`) — errcheck under golangci-lint already governs that, tuned. `G122` wants `os.Root` in `filepath.WalkDir` callbacks, which would stop following the symlinks templates legitimately use. `G706` is log injection in a CLI that logs to the user's own terminal. Everything else — G110, G204, G301, G302, G306 — is annotated per site or fixed. If a real path-traversal defect is ever suspected, drop `G304,G703` from `GOSEC_EXCLUDE` for the run rather than reasoning about it from the gate's silence.
- **`// #nosec Gxxx -- reason` is the ONE suppression form; `//nolint:gosec` alone does nothing to standalone gosec** (#372): golangci-lint's embedded gosec honours `#nosec` too, so a single leading `// #nosec` comment satisfies both tools and the paired `//nolint:gosec` is dead weight. Verified empirically: the same site with `//nolint:gosec // #nosec G204 -- ...` as a *trailing* comment was still reported by `gosec ./...` — gosec only matches `#nosec` at the start of the comment text, so it must lead, on the offending line or the line above it. The repo still carries ~20 trailing `//nolint:gosec` comments on lines whose rule is excluded repo-wide; convert them opportunistically, don't churn them all at once.

- **A `cases.Caser` from `golang.org/x/text` must NEVER be cached in a package-level var — construct it per call** (#379): `transform.String` calls `t.Reset()` on entry (`transform/transform.go:569`), which is why a shared Caser looks fine under sequential use and corrupts under concurrent use — two goroutines interleave `Reset` with `Transform` over the same `pDst`/`pSrc`, and it panics as `slice bounds out of range` deep inside x/text, looking like a third-party bug. There were TWO of these (`formats.titleCase` and a duplicate `template.titleCaser` backing the `title` filter); the ticket only knew about one, and fixing only that one would have left `{{ name | title }}` panicking. Both now route through `formats.CaseTitle`. The line that was deleted said `// titleCaser is a cached English title caser to avoid allocation per filter call` — that "optimisation" WAS the P1, and the measured cost of not doing it is 167ns->266ns against `CasePascal`'s existing 575ns/8 allocs. Do not re-cache it. `*regexp.Regexp` and `flect`'s inflection caches (RWMutex-guarded in v1.0.3) are genuinely safe and are not the same thing.
- **A concurrency bug needs a UNIT reproduction, not an end-to-end one — measure the detection rate before committing either** (#379): `TestUT_CasePascalCamel_ConcurrentUse` (64x500 direct calls) fails 5/5 on the broken code; the end-to-end `tag test --parallel 8` acceptance run fails only 2/20 on that same code. An IT test at 10% detection is a flake that passes on a broken tree, and CI runs `-failfast` without `-race`, so it would abort unrelated PRs. Keep the e2e run as manual acceptance recorded in the PR body. Note `internal/template/cache_test.go`'s `TestUT_Engine_Cache_ConcurrentAccess` already fanned 100 goroutines through a shared engine and still missed this for the bug's whole life — its template is `{{ name }}`, which touches no filter. A concurrency test only covers what its fixture actually exercises.
- **The three variable-aware commands share ONE reference definition — keep it that way**: `tag template lint`, `tag template variables` and `tag template rename-var` must agree on what counts as a `vars.*` reference. Since #337 they do so structurally: `lint` and `variables` call `vars.ScanRefs`/`vars.ScanNames` (`internal/vars/scan.go`), and all of them are built on the same `scanBlock`/`skipQuoted`/`blockTag`/`isWholeReference` helpers in `internal/vars/rewrite.go`. Before that, two copy-pasted regexes drifted from the rewriter and produced four user-visible defects at once. Any change to what a reference is belongs in `scanBlockRefs` + `rewriteBlock`, never in a caller. `FuzzScanRefsAgreesWithRenameWalker` and `TestIT_TemplateVarScan_ThreeCommandsAgree` enforce the agreement — if you make them fail, fix the walker, don't relax the test.
- **A line-by-line regex scan cannot see a Gonja block that spans lines**: the pre-#337 scanner ran `bufio.Scanner` then matched `\{\{...\}\}` per line, so `{{ vars.a\n ~ vars.b }}` was invisible entirely — not partially wrong, completely unseen. Greedy `[^}]*`/`[^%]*` also meant only the LAST `vars.X` in a block ever matched. If you reach for a regex over template source here, you are reintroducing both bugs; walk the blocks instead.
- **`{% raw %}`: the BODY is literal, the opening TAG is not**: `MaskLiterals` (deleted in #337) blanked the whole raw span including its opener, but `renameInExpressions` rewrites the opener like any other block. The scanner now matches the rewriter — a `vars.*` in `{% raw vars.x %}` IS a reference, while the body is skipped. Pinned in `TestUT_ScanRefs_DeliberateEdgeCases`; don't "fix" it toward the old masking behaviour without also changing rename-var, or the three commands diverge again.
- **The `history.RecordingFileWriter` must never wrap the dry-run writer**: it hashes each file *after* write to record undo state, but the dry-run writer writes nothing, so `HashFile` fails with `hash after write ...` and aborts the whole run after the first file. Fixed in `engine.NewGeneratorWithRecorder` by only wrapping when `!dryRun` (history is persisted only for real runs anyway — see `generate.go`'s `if !dryRun`). If you add a new recording writer, gate it on `!dryRun` too.
- **The `n.*` generator namespace carries case transforms ONLY, and unknown attrs render empty & silent**: `computeNameOptions` (`internal/template/context.go`) provides exactly `snake_case`/`pascal_case`/`camel_case`/`kebab_case`/`lower_case`/`upper_case`/`past`. `n.snake` (no `_case`), `n.plural`, `n.humanize` all render `""` with no error — inflection lives on filters over `name` (`{{ name | plural }}`). The docs (`.skills/SKILL.md`) used to show the wrong `n.snake`/`n.plural` forms; they now match the map. Verify with a `ExecuteToString("{{ n.x }}", ...)` probe before documenting a new `n.` attribute.
- **The scaffold positional `[project-name]` has two decoupled roles**: it *defaults* the `project_name` variable (an explicit `-m project_name=` wins — see `collectVars`, which only sets `Meta["project_name"]` when absent) AND *drives the output dir* when `--output` is unset (see `planOutput`, which prefers `opts.ProjectName` over `vars["project_name"]`). Keep these two paths in sync: changing one without the other reintroduces "positional silently overrode --meta" (the old bug) or "meta override moved the output directory" (the over-correction).
- **`--format` is shared plumbing now — don't hand-roll it**: `formatFlag(allowed...)`, `resolveFormat(c, allowed...)`, `cmdOut(c)` and `unknownFlagError` live in `internal/commands/flags.go`; the encoder policy lives in `internal/jsonout.Write`. A new command that emits JSON uses those, and follows the envelope rule written down in `jsonout`'s package doc: a LIST wraps under a noun key (`{"entries":[...]}`), a single object or report goes bare. There is deliberately no `{"ok":...,"data":...}` wrapper and no `schema_version` — four commands shipped bare objects before the convention existed. `resolveFormat` falls back to text only when `!c.IsSet("format")`, so hand-built test contexts keep working while `--format=""` is still rejected.
- **Order inside a command Action is fixed: reparse → check positional count → resolveFormat → do the work → write → return the exit code**: `reparseTrailingFlags` must run first or a trailing `--format` is invisible, and after it you must use the returned slice — `c.Args()`/`c.NArg()` are stale because the reparser does not mutate the context. The exit code goes last so a JSON consumer never races the write (see `checkAction`). Pass the command's own `xxxFlags()` slice to the reparser, as `templateLintFlags`/`scaffoldFlags` do; using `c.Command.Flags` breaks under hand-built test contexts.
- **Text output of every converted command is pinned by golden fixtures in `internal/commands/testdata/golden/`**: `TestUT_TextGolden` compares full bytes, because `assert.Contains` cannot see tabwriter column-width or trailing-whitespace drift. If one fails, the change is wrong — do NOT rerun with `-update-golden`. The fixtures' provenance is documented at the top of `golden_text_test.go`; the six #346 ones were captured before any source change, the four #345 ones by building `main` in a worktree. Regenerating a fixture from the working tree launders the regression it exists to catch.

- **There are TWO file-action vocabularies and they describe different axes — do not merge them**: `internal/fileaction.Action` (create/inject/append/overwrite/openapi-merge/skip) is the *outcome* — what TAG actually did to a file — shared by `generate`, `scaffold` and `undo`. `internal/template.Action` (capitalised `Create`/`Append`/`Inject`/`OpenAPI`) is the *declared directive* parsed from template metadata. `internal/graph` and `internal/commands/generate_info.go` lowercase the DECLARED one for already-shipped JSON, which is why #352 deliberately left them alone: `graph` maps `template.ActionOpenAPI` to `"create"` and `generate_info` ignores `action: openapi`, so folding them onto the outcome vocabulary would silently change shipped output. `templateupdate.MergeOp` is a third, deliberately separate thing (see the doc comment in `internal/fileaction/action.go`).
- **`FileOpDetail.DisplayOp()` exists to LIE consistently, and that is the point**: `generate --verbose` printed `modified` for both append and inject before #352, so `DisplayOp` still maps both to `"modified"` to keep the golden fixture byte-identical. The consequence, verified empirically: the golden test **cannot** catch a re-collapse of append/inject, and neither can the compiler (an untyped string constant converts implicitly to `Action`) nor `exhaustive` (disabled in `.golangci.yaml`). `TestUT_Generate_Details_AppendAndInjectAreDistinct` asserting the whole `[]FileOpDetail` by equality is the ONLY guard — if you weaken it to `assert.Contains` or switch it to assert on `DisplayOp()`, the data loss silently returns.
- **`history.Action` is a type ALIAS, so "only five values are persisted" is a comment, not a compiler rule**: `internal/history` re-exports five of `fileaction`'s six constants and deliberately omits `ActionSkip` (a skipped file was never written, so there is nothing to undo). But because the type is aliased rather than defined, `history.FileEntry{Action: fileaction.ActionSkip}` would still compile. This was an accepted trade-off — the alias is what kept ~30 existing call sites from churning, and `IsValid()` was declined as YAGNI. Enforce it in review.
- **`tag undo` silently no-op'd for `overwrite` and `openapi-merge` for as long as those actions existed**: `revertFile` (`internal/history/undo.go`) switched only on create/inject/append and fell through to `return nil`, so `Undo` counted the file as reverted and printed success while leaving it untouched. Fixed in #352 by adding both to the restore-from-backup case — safe because `RecordingFileWriter.snapshotBefore` backs up any pre-existing file before `WriteFile` and before `MergeOpenAPIFile`, exactly as it does for inject/append. The final `return nil` is kept on purpose so undoing a manifest from a NEWER TAG version does not hard-fail on an unknown action.
- **When a peer reviews a vocabulary change, expect it to conflate the vocabularies**: during #352 an AI peer filed a "Blocker: `revertFile` omits the legacy `modified` action from old manifests". `"modified"` was never persisted — it only ever existed as the in-memory `FileOpDetail.Op`. Before acting on any finding about on-disk history values, check with `git show main:internal/history/recorder.go` what the `RecordModify` call sites actually pass; that settles it in one command.
- **`reparseTrailingFlags` adoption was never enforced — `--format` was the accidental forcing function, and the guard test is now the deliberate one** (#375): twelve commands acquired the reparse as a side effect of gaining `--format` in #345–#354, because `resolveFormat` does not work without it. The six that never got `--format` (`lib add`, `lib edit`, `template new bundle`, `template new generator`, `template rename-var`, `generate agent-file`) silently dropped trailing flags for their entire lives. The fix is NOT to deduplicate the four-line idiom — that would not have prevented it. `TestUT_AllCommands_RejectUnknownTrailingFlag` in `root_commands_guard_test.go` walks `RootCommands()` and probes every command with positionals + own flags, so non-adoption now fails the build. Its predicate is `cmd.Action != nil && len(cmd.Flags) > 0 && (cmd.Args || cmd.ArgsUsage != "")` — `Args` and `ArgsUsage` are INDEPENDENT urfave/cli fields and `bundle.go`/`new.go` set both, so keying on `ArgsUsage` alone would exempt a future `Args:`-only command. A `withPositionals` wrapper was costed and declined (see #378): `cli.Command` has no `Metadata` field and `Action` is a named func type, so wrapper adoption cannot be detected structurally and the same behavioural probe would still be the guard.
- **`RootCommands()` is the single definition of the command tree — main.go must build from it and nothing else**: this is the `GlobalFlags()` lesson applied one level up. Before #375 the guard test would have had to walk a hand-maintained copy of `main.go`'s `Commands:` slice, which is precisely the drift that produced a wrong-from-birth golden fixture in #353. `CompletionCommand(tag)` stays appended in `main.go` on purpose — it takes the `*cli.App` itself, so it cannot live in `RootCommands`; it declares no positionals, so it is outside the guard's predicate anyway.
- **An `if c.NArg() < 1` check PASSES when a trailing flag inflates the count, so "loud vs silent" cannot be read off the source** (#375): the ticket classified `lib edit` and `generate agent-file` as loud NArg failures. Both are minimum checks, so `agent-file claude -o OUT.md` (NArg 3) sailed through and wrote `CLAUDE.md` with exit 0. Only `rename-var`'s 2..3 range check is genuinely loud. Build the binary and run it before trusting a failure-mode table — five of the six were silent, not three.
- **Four commands take positionals but declare no flags of their own, and they are deliberately OUTSIDE the reparse guard**: `lib rm`, `lib update`, `template test` and `generate info` read no context flag values at all, so reparsing there would accept a trailing `--dry-run` and then ignore it — strictly worse than urfave/cli's own unknown-flag rejection. The exclusion is recorded in a comment on `probeCommands`; if a future command in this group starts reading a global, bring it under the guard explicitly rather than widening the predicate.
- **`undo` calls `reparseTrailingFlags` but is correctly absent from the guard's 17-command census**: it is the 18th call site, declares no `ArgsUsage`/`Args`, and rejects any returned positional outright (`tag undo gen_123` used to silently revert the LAST generation instead of the named one). Do not "fix" the census by adding it.
- **`internal/formats` is the place byte-vs-rune bugs hide, and `utf8.ValidString` is the only assertion that survives a behaviour decision** (#381): `lowercaseFirst`'s `str[i+1:]` and `CasePast`'s `w[:1]`/`w[1:]` sliced at byte 1 and emitted the orphaned tail of a multibyte rune — invalid UTF-8 written into generated files at exit 0, through the `camel`/`past` filters and `n.camel_case`/`n.past`. `CaseSnake`/`CaseKebab`/`CaseTitle`/`CasePascal` were clean because they route through `strings.ToLower`/`cases.Title`, which are rune-aware; `splitWords` was clean because it walks `[]rune(s)`. Both sites now share `mapFirstRune` on `utf8.DecodeRuneInString` — do not add a third copy. `rune(str[0])` anywhere in this package is the same bug wearing a different hat (it decided `isCamel` from `0xC3`). Note a caseless script (CJK, Arabic) satisfies `w == strings.ToUpper(w)` and so takes `CasePast`'s **acronym** branch, which leaves it unchanged: that is the decided answer, pinned in `TestUT_Cases_MultibyteInput`, not an accident.
- **`--dry-run` meant "skip the file writes" and nothing else — five defects, zero behavioural tests, and the docs were right the whole time** (#383): `tag scaffold --dry-run` executed pre/post hooks, wrote `.tagconfig.json` and `.tag/history.json`, created the output dir, exited 1 on any project-wrapper template with `--output` (`GenerateTagConfig` wrote into a `projectRoot` subdir dry-run never created), and — under `--force`, or via the failure rollback on ANY error path — called `os.RemoveAll` on a pre-existing directory. Only the `w.dryRun` guards in `output.go` were real. `docs/commands/scaffold.md:46,185` already promised "without writing anything to disk or creating the output directory", so this was code contradicting shipped docs, not a behaviour change — check the docs before classifying a fix as a behaviour change. The two gates that are easy to get wrong: `prepareOutputDir` is gated at the REMOVAL only (its existence/safety checks are the useful half of a preview), and the rollback `defer` must be registered only on a real run — gating `MkdirAll` while leaving the defer makes the data loss fire MORE often. Skip hook *rendering* too, not just execution, or a malformed hook template aborts a preview that would never have run the hook. The reason five defects survived: the only two test references to `--dry-run` asserted the flag was REGISTERED. The suite passed identically with the feature working or deleted.
- **A data-loss test must assert surviving BYTES, never `DirExists` — and pair every negative with a positive control**: `executeScaffold` calls `MkdirAll` immediately after `prepareOutputDir`'s `RemoveAll`, so "the output directory still exists" passes on the broken tree. Assert a canary file's content plus a full before/after `listTree` — the listing also catches additions, folding in "wrote nothing". Drive the rollback test from an induced RENDER error, never from the wrapper-template crash: once that crash is fixed the run succeeds, the defer no-ops, and the test silently stops exercising the rollback. And every `DryRun:true` assertion needs a `DryRun:false` sibling, or a tree where scaffolding is broken outright satisfies the whole file.
- **`Scaffold.Run(opts)` takes Options independently of `NewScaffold(opts)` — never add a second reader of the same field** (#356): the writer's `dryRun` is set at construction, so when `executeScaffold` started reading `ctx.opts.DryRun` from `Run`'s copy there were two sources of truth and nothing forcing agreement. Constructing dry then running real returns **exit 0** with a project containing `.tagconfig.json` and no files. Every test passed the same `opts` to both calls, so none of them could see it. `Run` now syncs the writer, mirroring `SetRecorder` directly above it. All three production call sites happen to pass the same value — the fragility, not a live bug, is the thing to remember.
- **`--format json` non-interactivity cannot be tested without an injectable TTY probe — under `go test` the unfixed code already passes**: `GetPrompter` falls back to `NoopPrompter` whenever `!IsTTY()`, and tests never have a TTY, so `opts.NoInput = true` and the three prompt-site guards are all invisible to assertions. Deleting them leaves `internal/commands` fully green. The fix that made it testable at all was collapsing the three duplicated conditions (`resolveAddToLib`, `resolveTemplateName`, `handleCookiecutterDetection` — each read the `no-input` FLAG and built its own `InteractivePrompter`, bypassing the injected Noop one) into `nonInteractive(c, jsonMode)` over a package-level `isTTY` var a truth table can override. Do not "clean up" that var.
- **The `--format` conformance test needs no fixtures because `resolveFormat` runs before input validation — and that property is itself asserted**: `--format bogus` is exit 2 even against a nonexistent template in an empty dir, so the rejection half covers all 22 commands with zero setup. `TestUT_FormatConformance_RejectionNeedsNoFixture` pins it: move `resolveFormat` after input validation and the census keeps passing while every rejection row silently starts reporting a missing-fixture error instead. Scope probes to each command's arity — handing a positional to a command that takes none makes urfave/cli hunt for a subcommand and fail with "No help topic" long before `resolveFormat` runs, asserting nothing. And "exactly one JSON document" means decode once then demand `io.EOF`; `json.Unmarshal` accepts trailing content.
- **Commit before spawning any subagent that can reach the working tree**: during #356's review both an in-repo reviewer and Antigravity (which edited files despite an explicit read-only instruction) ran `git checkout --` / `git restore --source=HEAD --worktree` to undo their own edits. Neither can distinguish its changes from the caller's, so both wiped uncommitted main-loop work — twice, silently, while the main loop was mid-edit. Codex separately OOM'd (exit 137) on 3 of 4 invocations this session; when a peer is down, record reduced consensus confidence rather than implying agreement.
- **`GlobalFlags()` is the single definition of the App-level flags — do not re-declare them anywhere**: `--dry-run`, `--path`, `--shared-path` and `--bundle-path` live on the `cli.App` (not on any command), and `internal/commands.GlobalFlags()` is what both `main.go` and the test harness (`newTestApp`) build from. They had drifted before #353: the test App declared no flags at all, so `c.String(PathFlag)` read back `""` instead of `.tag` and a golden fixture recorded a path the shipped binary never prints. A command reads these through the context lineage without declaring them, which is also why `reparseTrailingFlags` registers `c.App.Flags` — see the next entry.
- **`reparseTrailingFlags` registers `c.App.Flags` as well as the command's own, and that is load-bearing**: without it, a trailing `--dry-run` on `generate`/`convert` is rejected as an unknown flag; with only the command's flags it was silently dropped. `cli.Context.Set` resolves a name through `Lineage()` child-to-parent, so no plumbing is needed beyond the lookup table, and a command-local flag of the same name still wins (this is why `scaffold`, which declares its own `dry-run`, is unaffected). Adding the reparser to a command is a behaviour change: it makes previously-ignored trailing flags take effect. Verify with a differential run against a `main` build before assuming "no text drift" — that is how `convert -o` and `generate --verbose` were found to be silently broken.
- **`undo --list` emits `file_count`, never `files`**: across this repo `files` is always an ARRAY (`generate`'s document, `rename-var`, `history.Generation`, `templateupdate`'s manifest and summary) and scalar counts are `*_count` (`file_count`, `reference_count`, `total_count`). `tag undo`'s own document uses `files` for the per-file array, so emitting a number under the same key from the same command was a shape collision. Renamed before anything consumed it.
- **Never hand `templateupdate.UpdateResult`, `MergeResult` or `ConflictReport` to `jsonout.Write`**: `Applied[].Content` and `ConflictedFile.{Base,Ours,Theirs,Merged}Content` are unbounded copies of the user's own source. `update` maps through `updateFileJSON`/`updateConflictJSON`, which carry only paths and scalars. `TestUT_UpdateJSON_NeverLeaksFileContent` guards this and checks base64 as well as plaintext (json renders `[]byte` as base64, so a plaintext-only search cannot see the leak) — and self-checks that the detector fires on a leaky struct, so do not weaken it.
- **`fileutil.CopyDir` calls `os.MkdirAll` before EVERY file, so a concurrent writer never truncates itself — the corruption is a MIXED tree, not a partial one** (#397): the ticket (and the obvious hypothesis) said writer A mid-`CopyDir` gets cut short when writer B `RemoveAll`s the destination. It does not: A transparently re-creates the directory B just deleted and keeps going, and `WalkDir` is one-pass so A never revisits what it already wrote. Both writers' files end up interleaved under one `_meta.json`, which `Get` then serves as a HIT indefinitely. Any oracle that only looks for MISSING files will not see this — check for wrong CONTENT and for both writers' unique marker files. Measured 127/200 files mixed in a two-writer round.
- **The cache base dir has exactly three `os.ReadDir` consumers and a staging directory must be handled in all three** (#397): `Cleanup`, `List` and `ClearAll` in `internal/remote/cache.go`. A staging dir carries a valid `_meta.json` (written into the stage before the rename, so the entry becomes visible complete-with-metadata in one step), which means it passes `ClearAll`'s "did TAG write this?" ownership gate — `ClearAll` would delete a live stage out from under a concurrent `Set`, and timed between `commit`'s two renames it takes the `.prev` too, losing the new AND the previous entry. `Cleanup`/`ClearAll` therefore reap staging dirs only when older than `staleStagingAge` (24h) via one shared `reapIfStaleStaging`; `List` skips them outright and never deletes. Reaped stages deliberately do NOT count toward the `removed` tally the user sees. Consequence to keep in mind: `tag cache clear --all` intentionally leaves a recent `.staging-*` behind, and that is documented in `docs/reference/remote-refs.md`.
- **`commit`'s `.prev` cannot be recovered after a crash, and that is by design — don't "fix" it**: a peer filed restoring it as a Blocker. The name is `.staging-<random>.prev` and encodes no cache key, so nothing can map it back to an entry; cache data is regenerable and a refetch self-heals. The real defect that review found was a comment claiming a staging dir "was never a cache entry", which is false for `.prev`.
- **`--format`-style plumbing has a sibling now: `fileutil.WriteFileAtomic` is the ONE way to write a file that must not be observed half-written**: `internal/replay`, `internal/library`, `internal/history` and `internal/templateupdate` each had their own `CreateTemp`/write/close/rename copy with its own gosec suppression, none fsynced, and one discarded its `Close` error and could publish truncated JSON at exit 0. Adding a fifth hand-rolled copy re-opens all three bugs. `MkdirUnique` is its directory counterpart; both create with the caller's mode through `O_CREATE`/`os.Mkdir` specifically so the umask still applies (see the go-backend lesson on `Chmod`).

- **The shared `vars` walker now tracks SCOPE, and both walkers must stay in lockstep** (#393): `vars` is an ordinary identifier to Gonja, so `{% for vars in items %}{{ vars.alpha }}{% endfor %}` refers to the loop variable, not the declared variable `alpha`. Before `internal/vars/shadow.go`, the purely-lexical walker claimed it — which made `template rename-var` rewrite the shadowed reference and silently change what the template rendered (verified against a `main` build, not theorised), and made `DeclaredDeps` invent a self-edge that aborted `scaffold` with `circular variable dependency` on a template that had worked. `varsShadow` tracks the only four constructs that can bind a name (`for`, `with`, `macro`, `set`); non-shadowing `for`/`with`/`macro` blocks are still pushed so their end tag pops the right entry, and `if`/`endif` never participate. Two invariants: a block's own references are handled BEFORE `observe` (the RHS of `{% for vars in vars.items %}` is the enclosing scope), and `ScanRefs` and `renameInExpressions` must apply it identically or `FuzzScanRefsAgreesWithRenameWalker` diverges — it ran 13.5M execs clean.
- **`depends_on` is gated on `ContainsTemplateExpression`, and that gate is load-bearing** (#393): the predicate is `strings.Contains(s,"{{") && strings.Contains(s,"vars.")`, which is what `IsDerived`/`IsEvaluatedDefault` use. So `{% if vars.x %}` (no `{{`) and `{{ vars["x"] }}` (no `vars.`) are NOT expressions to TAG — their defaults are literal strings that are never rendered. `ScanNames` finds references in both, so scanning ungated invents dependency edges for values TAG never evaluates, and keeps `depends_on` inconsistent with `default_is_expression`. `TestUT_TopologicalSortVars_StatementOnlyDefaultIsNotADependency` fails if the gate is removed — that is its whole purpose, so do not "simplify" it away as a test that passes on old code (it does; it is a gate guard, not a change pin).
- **`Reference.CacheKey()`'s readable prefix is lossy — the identity digest is the actual key**: owner and repo are validated only for path traversal, so both may contain the `_` used as separator, and `sanitizeForPath` folds `/`, `:`, `*` and more onto `_` too. `gl:a_b/c` and `gl:a/b_c` both flattened to `gl_a_b_c`, and since `tryCache` trusts the key alone and never re-checks `CacheMeta.OriginalRef`, one repo was served the other's template and (via #393's `resolved_commit`) the other's SHA. A 12-char digest over NUL-joined (provider, owner, repo, version) now guarantees uniqueness for all inputs rather than for the characters today's sanitizer catches. `SubPath` is deliberately OUT of the identity — an entry caches the whole repo and `applySubPath` selects within it; epic #388 records that separately. Tests must derive keys via `Parse(...).CacheKey()`, never hardcode them.
- **Two AI reviewers on the same diff are not redundant — they disagreed on whether it was shippable** (#393/#395): Antigravity reviewed the diff and returned "no correctness defects found" with a confident per-area breakdown. Codex, on the identical diff, found a fatal regression (the `vars` shadowing self-cycle) plus a real pre-existing cache-key collision. A single clean review is not evidence of correctness. Also: verify each finding empirically before acting — of Codex's four, two were real defects, one was real-but-pre-existing (out of scope), and one measured a gate guard against the wrong baseline.

- **`ConvertPath` rewrites `{{ cookiecutter.x }}` to `{{ vars.x }}` IN PLACE — there is no `__x__` form**: the `convert` help text claimed otherwise for a long time and #355's ticket body repeated the doubt. The `__var__` convention does exist in TAG, but for scaffold path placeholders, an unrelated mechanism. Verify against the binary before documenting either.
- **`Command.OnUsageError` fires with a NIL flag set, so the failing command's own context cannot answer any question about its flags** (#396): `Command.parseFlags` (`urfave/cli@v2.27.7/command.go:315-336`) returns `nil, err` on ANY parse error and `Command.Run` unconditionally does `cCtx.flagSet = set` right after, so inside `OnUsageError` the context's flag set is nil — `c.Args()` PANICS outright and `c.String("format")` reads back empty regardless of where `--format` sat in argv. The workaround is not to ask that context at all: `c.Lineage()[1]` (the parent) has an intact flag set and its `Args()` still holds the full raw argv, in both argument orders, which is what `jsonRequestedInArgs` scans. That scan must be flag-ARITY aware or it reads a value as a flag — `scaffold --bogus --output --format json` has `--output` swallow `--format`, so a naive grep for the token flips a text-mode run to JSON. It must also stop at `--`. Do not trust a claim that this branch is dead code: an earlier revision of this very entry said so, and it was wrong — build the binary and run both orders.
- **A same-named test helper already living in the package under test blocks a new production function of the same name — grep before naming**: `internal/commands/diff_test.go` had its own private `exitCodeOf(err error) int` test helper (nil→0, generic `cli.ExitCoder`) years before #396 needed a production `exitCodeOf` with different semantics (mirrors `main.go`'s `*app.CommandError`-only extraction exactly). Since Go test files share the package namespace, this is a hard compile collision, not a lint nit. Renamed the pre-existing test-local helper (`diffExitCodeOf`, 2 call sites, one file) rather than deviating from the approved spec's production function name — a pure rename carries zero behavior risk and keeps the two exit-code concepts (test assertion helper vs. main()-mirroring production logic) named for what they actually do.
- **`findProjectWrapper` now returns `(wrapper string, siblings []string, err error)`, and a wrapper only unwraps when `siblings` is empty** (#403): a Cookiecutter-style wrapper directory beside OTHER root content (a sibling `hooks/` dir, a stray root file) used to unwrap anyway and silently drop the siblings — `project_root` pointed at the wrapper subdir while `output_dir` held files the docs never mentioned. Now content beside the wrapper suppresses unwrapping entirely: the whole root is written flat, `project_root == output_dir`, and `planOutput` prints a warning (via `s.output`, so it lands on stderr under `--format json` — verified through the JSON/text stream split `internal/commands/scaffold.go` already had) naming each sibling and pointing at `.tagignore`. Because `tag convert`'s own output always puts `hooks/` beside the wrapper, `Converter.Convert` now writes (or appends to) a `.tagignore` excluding `hooks/` whenever it copies at least one hook — otherwise every converted template would stop unwrapping and leak its hook script into generated projects. That write must happen AFTER `processTemplateFiles`, not right after `CopyHooks`: `destDir` doesn't exist yet at that point on a fresh conversion (step 4 either skips creation or `RemoveAll`s it), and a SOURCE-provided `.tagignore` only reaches `destDir` via the file walk — write before the walk and it gets clobbered instead of appended to.
- **A `t.TempDir()` path embeds the test's own name — a bare `assert.NotContains(stdout, "Warning")` can false-positive on the temp path, not a real leak**: chasing this cost a full debug cycle (`t.Logf` the index, then the quoted string) before the cause was obvious — `TestIT_Scaffold_MixedRootWarning_GoesToStderrNotStdout`'s own name contains "Warning" (`...MixedRootWarning...`), and that name is baked into `output_dir`/`project_root`, which legitimately appear in the JSON on stdout. Assert on a phrase from the actual message body (`"Not unwrapping"`), never on a single common word, when the oracle is "this text must not leak into stdout" and the test's own name could plausibly contain that word.
- **`nilerr` (golangci-lint) triggers on the STRUCTURE `if errLike != nil { return ..., nil }`, not on the variable being literally named `err`** — renaming `err` to `readDirErr`/`statErr` alone does not silence it. Two real fixes: (1) invert to the positive-condition form used elsewhere in this repo, `if x, e := f(); e == nil && cond { ...only success path... }` with a single trailing `return nil` outside any error check, or (2) push the check into a small helper that returns `(T, bool)` instead of `(T, error)`, so there is no error value in the caller's scope for the linter to match against. Both preserve the deliberately tolerant "missing dir/file is not a hard failure" behavior the pattern exists for.

- **`OutputWriter.Write` has TWO path anchors and they are not interchangeable** (#412): `relPath` is relative to the TEMPLATE ROOT and drives `isRootMetadataFile` plus `.tagignore` matching; `outRel` is relative to the WALK ROOT and drives `ProcessPath`, `destPath`, `files[].path` and `isInternalTree`. Before #412 there was one path, and unwrapping (which points the walk at the wrapper) silently moved both decisions with it — a root `.tagignore` stopped being read, and `<wrapper>/tag.template.json`/`.tagignore`/`_meta.json` vanished from disk AND from `files[]` at exit 0. `isSkippedEntry` was split into two predicates precisely so the differing anchors are named rather than implied; feeding either one the other's path reintroduces a shipped bug. Note the deliberate asymmetry: wrapper-level TAG **filenames** are content, wrapper-level `_generators/`/`_dialects/`/`.tag/` **directories** are not, because they would land in the `projectRoot/.tag/` that `finalizeRun` and `copyGeneratorsToOutput` write into. `.tagignore` patterns are template-root-relative, which is what `docs/templates/authoring.md` already documented — check the docs before classifying a change here as a behaviour change.
- **`runContext.unwrapDir` is the ONLY unwrapping signal — do not reintroduce a derived path field**: it replaced `effectiveTemplateDir`, which existed solely so `finalizeRun` could ask `effectiveTemplateDir != opts.TemplateDir`. One field, one writer (`planOutput`'s unwrap branch), two readers. `Write` joins it onto the template root only when non-empty, deliberately: `filepath.Join(root, "")` Cleans, so joining unconditionally changes the spelling of `./tmpl` to `tmpl` in the symlink warning and makes the no-unwrap path merely equivalent rather than bit-identical.
- **Removing an abort means auditing what that abort was accidentally protecting** (#335): `LoadTemplateFiles` loaded a generator's `tag.template.json` as a template, which aborted `tag generate` — the reported bug. But `generateTemplate` swallowed both the read error and the parse error on that same file (`if data, readErr := os.ReadFile(...); readErr == nil` around `ParseTemplateConfig`), so the abort was the ONLY thing stopping a malformed or unreadable config from silently disabling the `requires` gate it declares. Skipping the file turned a loud failure into a fail-open, verified against a `main` build in both directions rather than reasoned about. Same shape one level up: the bundle path never read a bundled generator's own `tag.template.json` at all, and nobody noticed because a generator declaring `requires` could not run in a bundle in the first place. All three readers now share `readGeneratorConfig` in `internal/commands/prereq.go` — missing file is an empty config, anything unreadable or unparseable is fatal. When a fix deletes an error path, list what else depended on that error firing.
- **`LoadTemplateFiles` also loads `_shared/`, so anything filtered there is filtered for includes too** (#335): the skip is one line in one loader with six production invocations across four functions (`engine.go:40/46/80/85`, `graph/analyzer.go`, `commands/generate_info.go`). The shared path never aborted — its map feeds `CreateMemoryLoaderFromMap`/`SetSharedContent`, never `Parse` — so the only consequence is that `{% include "tag.template.json" %}` against a shared file with that exact name stops resolving. A two-loader split (raw for `_shared`, filtered elsewhere) was proposed by a peer, costed, and declined: it recreates the engine/graph disagreement this ticket exists to remove, and every one of the six call sites would have to keep choosing correctly. The filter keys on the SOURCE filename, so a meta-generator can still emit a `tag.template.json` by naming its source something else and setting `to:`.
- **The `internal/graph` skip it replaced was inert, and "output unchanged" is proven by a differential run, not by a unit test**: `ExtractMetadata` needs two lines that trim to exactly `---`, which valid JSON cannot produce, so `parseTemplateAction` already returned `(nil, nil)` — no action, no warning. `TestUT_AnalyzeSkipsTagTemplateJSON` therefore passes with the skip present, with it removed, and on pre-fix code; it is a no-change guard, not regression coverage, and the test says so. What actually discharges the acceptance criterion is `tag template graph` run against a `main` worktree build over a fixture holding the config plus a create template, an inject template and a no-frontmatter file, diffed byte-for-byte in text AND `--format json`.
- **Two AI peers cleared the shared-path question that the third correctly flagged** (#335): Antigravity argued from the reserved-name convention and the QE agent said not to pin the semantic; only Codex checked `SetSharedContent` and found the include actually resolves today. Its Q1 conclusion (split the loader) was still declined, but the FACT it surfaced is what turned an unexamined assumption into a recorded, operator-approved trade-off. Codex's diff review then found the `requires` fail-open that all three of us — and the ticket — had missed. Reviewing the approach and reviewing the resulting diff catch different things; do both.
